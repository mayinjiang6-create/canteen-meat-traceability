# 接口文档

> 文档编号：TECH-03 ｜ 版本：v1.1 ｜ 定稿：2026-11-18
> Base URL：`http://localhost:8080/api` ｜ 风格：REST ｜ 编码：UTF-8
> 关联：`TECH-02 数据库设计`、`TECH-04 合约设计`
>
> **v1.1 变更（2026-11-18，阶段 B 第 2 周实装）**：原计划的 `/events/cold-chain`、`/events/disposal`、`/events/recall`
> 三个动作式路径，实装时改为资源化路径 `/cold-chain-logs`、`/abnormal-events`、`/recalls`。
> 原因是异常与召回各有独立生命周期（登记→处置、发起→完成），塞在一个 `/events` 下面无法表达资源状态，
> 也没法做"按批次查我的异常"这类列表查询。功能与字段口径不变。

## 1 通用约定

### 1.1 统一返回体

```json
{
  "code": 0,
  "message": "ok",
  "data": { },
  "traceId": "b3f2c1d4e5a6",
  "timestamp": "2026-11-18T18:30:00+08:00"
}
```

- `code = 0` 表示业务成功，**HTTP 状态码同时为 200**
- 业务失败时 HTTP 仍返回 200，`code` 非 0，`data` 为 `null`
- 仅鉴权失败返回 401，系统级异常返回 500
- `traceId` 贯穿日志，排查问题时先看它

### 1.2 分页

请求：`?page=1&size=20&sort=createdAt,desc`
响应 `data`：

```json
{ "page": 1, "size": 20, "total": 137, "records": [ ] }
```

`size` 上限 100，超出按 100 处理。

### 1.3 时间与数值

| 类型 | 格式 | 示例 |
|---|---|---|
| 时间（入参） | `yyyy-MM-dd HH:mm:ss` 或 ISO-8601 | `2026-11-18 09:30:00` |
| 时间（出参） | ISO-8601 带偏移 | `2026-11-18T09:30:00+08:00` |
| 数量 | 字符串，定点 3 位小数 | `"120.000"` |
| 金额 | 字符串，定点 2 位小数 | `"26.50"` |

> 出参数量刻意用**字符串**而非数字：JavaScript 的 `Number` 是双精度浮点，`120.001` 在前后端往返后可能变成 `120.00099999999999`，直接导致摘要比对失败。

### 1.4 鉴权

- 登录后返回 `token`，后续请求带 `Authorization: Bearer {token}`
- 公开接口（`/api/public/**`）免鉴权
- 存活探针 `/api/health` 免鉴权，**只证明进程活着**（不查库、不查链），供容器 HEALTHCHECK 与负载均衡摘流使用
- 角色：`ADMIN`（统一管理员，全部写权限）、`SUPPLIER`（只读自己相关数据）、`VIEWER`（只读）

### 1.5 幂等

所有 **POST 写接口** 支持请求头：

```
X-Request-Id: 9f2a7c31-4b8e-4d1a-9c22-0b7f5e6d3a11
```

同一 `X-Request-Id` 在 24 小时内重复提交，返回首次结果（`code=0`，`data.replayed=true`），不新建记录（BR-10）。缺省时服务端按 `用户+接口+参数摘要` 兜底去重。

## 2 错误码

| code | HTTP | 含义 | 前端处理 |
|---|---|---|---|
| 0 | 200 | 成功 | — |
| 40001 | 200 | 参数校验失败 | 表单标红，提示 `message` |
| 40002 | 200 | 数量格式非法（非 3 位小数） | 提示重填 |
| 40101 | 401 | 未登录或 token 过期 | 跳登录页 |
| 40102 | 403 | 无权限 | 提示"无操作权限" |
| 40401 | 200 | 资源不存在 | 提示并返回列表 |
| 40901 | 200 | 数量不足（可用余量不够） | 提示剩余可用量 |
| 40902 | 200 | 状态不允许该操作 | 提示当前状态 |
| 40903 | 200 | 重复请求（幂等命中，非错误） | 静默复用结果 |
| 40904 | 200 | 来源重复引用同一批次 | 高亮冲突行 |
| 40905 | 200 | 事件摘要冲突 | 红色告警，引导联系管理员 |
| 42901 | 429 | 请求过于频繁 | 退避重试 |
| 50001 | 200 | 存证提交失败 | 提示"已入库，存证待重试" |
| 50002 | 200 | 链上不可达 | 提示"暂无法核验" |
| 50003 | 200 | 大模型调用失败 | 降级为仅展示检索结果 |

### 4.2 POST `/purchases` 创建采购批次

**请求**

```json
{
  "supplierId": 3,
  "meatType": "猪肉",
  "origin": "江西省南昌市",
  "slaughterNo": "SL20261116-07",
  "quarantineNo": "JY-360100-20261118-0042",
  "quantity": "120.000",
  "unit": "kg",
  "unitPrice": "26.50",
  "arriveTime": "2026-11-18 08:40:00",
  "coldChainTemp": "3.50"
}
```

**响应**

```json
{
  "code": 0,
  "data": {
    "id": 101,
    "batchNo": "PB20261118001",
    "status": "PENDING_ACCEPT",
    "availableQty": "120.000",
    "evidence": { "eventId": "6f1c...0718", "status": "PENDING" }
  }
}
```

**要点**：返回 `evidence.status = PENDING` 是正常的——业务已落库，存证异步进行。前端不要因此报错。

**错误**：`40001` 供应商不存在 / 检疫证号为空；`40903` 重复提交。

### 4.3 POST `/acceptances` 验收登记

**请求**

```json
{
  "batchId": 101,
  "acceptTime": "2026-11-18 09:30:00",
  "inspector": "李四",
  "temperature": "3.50",
  "appearanceOk": true,
  "certComplete": true,
  "sampleRetained": true,
  "result": "PASS",
  "rejectReason": null
}
```

**响应**

```json
{
  "code": 0,
  "data": {
    "acceptNo": "AC20261118001",
    "batchNo": "PB20261118001",
    "batchStatus": "PASSED",
    "evidence": { "eventId": "a71b...", "status": "PENDING" }
  }
}
```

**规则**：

- `result=PASS` → 批次 `PENDING_ACCEPT` → `PASSED`
- `result=FAIL` → 批次 `PENDING_ACCEPT` → `REJECTED`（限制流转），`rejectReason` 必填
- 已验收过的批次重复提交 → `40902`

### 4.4 POST `/process-batches` 加工投料（多来源）

**请求**

```json
{
  "meatType": "猪肉",
  "processTime": "2026-11-18 10:20:00",
  "workshop": "一食堂后厨",
  "operator": "王五",
  "retainSampleNo": "LY20261118001",
  "outputQty": "120.000",
  "sources": [
    { "purchaseBatchNo": "PB20261118001", "usedQty": "80.000" },
    { "purchaseBatchNo": "PB20261118002", "usedQty": "40.000" }
  ]
}
```

**响应**

```json
{
  "code": 0,
  "data": {
    "id": 55,
    "processNo": "PR20261118001",
    "status": "CREATED",
    "inputQty": "120.000",
    "outputQty": "120.000",
    "sources": [
      { "purchaseBatchNo": "PB20261118001", "usedQty": "80.000", "remainQty": "40.000" },
      { "purchaseBatchNo": "PB20261118002", "usedQty": "40.000", "remainQty": "60.000" }
    ],
    "evidence": { "eventId": "c0d3...", "status": "PENDING" }
  }
}
```

**规则（全部在单事务内校验）**：

| 校验 | 违反 |
|---|---|
| 各来源批次存在且 `status=PASSED` | `40902`（`CLOSED` 同样不可再投料） |
| 来源不重复 | `40904` |
| 单个来源 `usedQty ≤ available_qty` | `40901` |
| `outputQty ≤ Σ usedQty` | `40001` |
| 事务内乐观扣减 `available_qty` | 受影响行数为 0 时 `40901` |

**实现备注**：

- 来源批次按 `purchaseBatchNo` **升序**扣减，保证并发事务的加锁顺序一致；预校验只用于提示，权威判定是条件更新。
- 扣到 `available_qty = 0` 时该采购批次自动 `CLOSED`（状态字典 6.1）。
- `inputQty` 不落库，由 `source_relation.used_qty` 汇总得出——来源关系一变，投入量自动跟着变。
- `40901` 的提示里给出的是**当前读**到的真实剩余量（并发下快照读会给出过期的数字）。

### 4.4.1 POST `/process-batches/{id}/onsale` 上架

**响应**：加工批次详情（`status = ON_SALE`）。

**规则**：仅 `CREATED → ON_SALE`；已 `ON_SALE` 再调按幂等返回成功；其余状态返回 `40902`。

**不生成存证事件**：`TECH-02` 6.4 定义的 9 类事件里没有"上架"——它是内部状态流转，
不是需要向社会公示的可核验事实。为凑数发明事件类型只会让链上多出看不懂的记录。

### 4.4.2 GET `/process-batches/{id}` 详情

返回单个加工批次 + `sources[]`（含上游批次号、投入量、当前余量、供应商名称）。
列表接口 `GET /process-batches` 带 `inputQty` / `sourceCount` 汇总，但不返回 `sources`，避免响应过大。

### 4.5 POST `/sales` 销售登记

**请求**

```json
{
  "processBatchNo": "PR20261118001",
  "channel": "一食堂 3 号窗口",
  "quantity": "25.000",
  "unitPrice": "38.00",
  "saleTime": "2026-11-18 11:30:00",
  "operator": "赵六"
}
```

**响应**

```json
{
  "code": 0,
  "data": {
    "id": 91,
    "saleNo": "SL20261118001",
    "processNo": "PR20261118001",
    "channel": "一食堂 3 号窗口",
    "quantity": "25.000",
    "unitPrice": "38.00",
    "amount": "950.00",
    "saleTime": "2026-11-18T11:30:00",
    "operator": "赵六",
    "status": "NORMAL",
    "processStatus": "ON_SALE",
    "availableQty": "95.000",
    "evidence": { "eventId": "7f3a...", "status": "PENDING" }
  }
}
```

**规则（单事务）**

| 校验 | 违反 |
|---|---|
| 加工批次存在 | `40401` |
| 数量 > 0 | `40001` |
| 批次状态必须是 `ON_SALE`（BR-06 / BR-09） | `40902` |
| 销售数量 ≤ `available_qty`（BR-07） | `40901` |
| 扣减到 0 → 批次 `ON_SALE → SOLD_OUT` | —— |

**实现备注**

- **权威判定是条件 UPDATE**：`WHERE status='ON_SALE' AND available_qty >= #{qty}`，受影响行数为 0 才回查原因。预校验只负责给出人话提示，不承担正确性责任——中午 11:30 两个窗口同时卖同一批净菜是常态，先查再改必然卖超。
- **失败原因先判状态、再判余量**：一个刚被召回的批次如果提示"余量不足"，会把责任推给库存，掩盖真正的原因。
- `amount` 由服务端算（quantity × unitPrice，2 位小数）：让前端各自乘一遍，迟早出现两个页面两个金额。
- `processStatus` / `availableQty` 返回的是**扣减后**的值（重新读库），窗口端据此判断"这一单卖完是不是就售罄了"。
- 每次销售生成一条 `SALE_CREATE` 事件（`batchId` = 加工批次号），公开页沿追溯码就能看到"这批肉卖到了哪个窗口"。

### 4.6 POST `/cold-chain-logs` 冷链温控登记

**请求**

```json
{
  "batchNo": "PB20261118001",
  "segment": "WAREHOUSE_TO_CANTEEN",
  "transportNo": "TR-20261118-001",
  "temperature": "6.50",
  "recordedAt": "2026-11-18 06:20:00",
  "recorder": "司机王五",
  "remark": "途中冷藏机故障 20 分钟"
}
```

**响应**

```json
{
  "code": 0,
  "data": {
    "id": 12,
    "logNo": "CC20261118001",
    "batchNo": "PB20261118001",
    "meatType": "冷鲜猪肉",
    "segment": "WAREHOUSE_TO_CANTEEN",
    "transportNo": "TR-20261118-001",
    "temperature": "6.50",
    "threshold": "4.00",
    "exceeded": true,
    "recordedAt": "2026-11-18T06:20:00",
    "abnormalNo": "AB20261118001",
    "evidence": { "eventId": "b21c...", "status": "PENDING" }
  }
}
```

**规则**

| 项 | 口径 |
|---|---|
| `segment` | 只允许 `ORIGIN_TO_WAREHOUSE`、`WAREHOUSE_TO_CANTEEN`，其余 `40001` |
| 阈值 | **不由录入人填**，按品类从 `trace.cold-chain.*` 取：含「冻」→ −15℃、含「牛」→ 4℃、含「猪」→ 4℃、其余兜底 4℃ |
| 超限判定 | 严格大于阈值（恰好等于算合规），超限时按超出度数分 `LOW`（≤0.5℃）/ `MEDIUM`（≤2℃）/ `HIGH` |
| 超限后果 | 自动开一条 `TEMPERATURE_EXCEEDED` 异常工单（`abnormalNo` 随响应返回），**但不改采购批次状态** |
| 存证 | 每次登记都生成 `COLD_CHAIN` 事件（payload 含 temperature / threshold / exceeded） |

**为什么登记不改批次状态**：温度超标不等于整批拒收。要不要退货、销毁还是降级使用，是处置环节的判断；登记环节擅自把批次置 `REJECTED`，等于让司机替验收员做决定。

### 4.7 异常登记与处置

**4.7.1 POST `/abnormal-events` 登记**

```json
{
  "processBatchNo": "PR20261118001",
  "abnormalType": "SENSORY_ABNORMAL",
  "level": "HIGH",
  "description": "抽检发现色泽异常，暂停销售待复检",
  "occurredAt": "2026-11-18 10:05:00",
  "handler": "张管理员"
}
```

`processBatchNo`（成品问题）与 `batchNo`（到货问题）**至少填一个**，都为空返回 `40001`。

**效果（单事务）**：插入异常记录（`status=OPEN`）；若关联的加工批次当前是 `ON_SALE`，**同时置为 `ABNORMAL`**（销售入口立即失效）；生成 `DISPOSAL` 事件，payload 带 `stage=REPORTED`。

> 只冻结 `ON_SALE`：`SOLD_OUT` 是"卖完了"的事实，为了一条异常把它改成 `ABNORMAL`，等于篡改历史。

**4.7.2 POST `/abnormal-events/{id}/dispose` 处置**

```json
{
  "action": "暂停销售、封存留样并送第三方复检",
  "handler": "张管理员",
  "conclusion": "复检合格，恢复销售",
  "resumeSale": true,
  "disposeTime": "2026-11-18 15:40:00"
}
```

**效果（单事务）**：异常 → `CLOSED` 并写 `closed_at`；`resumeSale=true` 时批次 `ABNORMAL → ON_SALE`；再生成一条 `DISPOSAL` 事件（`stage=CLOSED`）。

- `resumeSale` 必须显式传：处置结论可能是"整批销毁"，按"有结论就恢复"的默认逻辑会把销毁的批次重新上架。
- `resumeSale=true` 但批次已不是 `ABNORMAL`（例如期间被召回）→ `40902`，整笔回滚，不留"已处置但没恢复"的半截记录。
- 同一异常会留下**两条** `DISPOSAL` 事件（登记 / 结案）。这是刻意的：登记是"发现了问题"，结案是"问题处理完了"，两件事都得可核验。

```json
}
```

**响应**

```json
{
  "code": 0,
  "data": {
    "id": 3,
    "recallNo": "RC20261118001",
    "processNo": "PR20261118001",
    "reason": "同批次抽检发现兽药残留超标",
    "affectedSales": 3,
    "recalledQty": "28.000",
    "recallTime": "2026-11-18T16:00:00",
    "status": "INITIATED",
    "processStatus": "RECALLED",
    "evidence": { "eventId": "e9c1...", "status": "PENDING" }
  }
}
```

**效果（单事务，三处写入缺一不可）**

1. `process_batch` → `RECALLED`（挡住后续销售）
2. 该批次**全部** `sale_record.status` → `RECALLED`，`affectedSales` = 本次被标记的笔数
3. 写 `recall_record` + `RECALL` 事件（payload 含 reason / scope / affectedSales / recalledQty）

**实现备注**

- **加锁顺序与销售一致**（先 `process_batch` 行、再 `sale_record` 行）。顺序反了就会与销售登记交叉等锁，形成死锁。
- `recalledQty` 在**标记之后**汇总：此时该批次的销售记录已全部是 `RECALLED`，并发卖出的最后一笔也算得进去。
- 重复召回：批次已是 `RECALLED` 时返回最近一张召回单（`replayed=true`），而不是报"状态不允许"——按钮双击不该被当成错误。
- 召回只标记、不删除销售记录：已售出是事实，`RECALLED` 是它的结论。

### 5.2 GET `/public/trace/{batchNo}/verify`

只返回核验结论，供页面轮询刷新用（不重复拉全量时间线）。

```json
{
  "code": 0,
  "data": {
    "batchNo": "PR20261118001",
    "overall": "PARTIAL",
    "counts": { "matched": 6, "mismatched": 0, "unconfirmed": 1, "unreachable": 0 },
    "events": [
      { "eventId": "a71b2c...", "verifyStatus": "MATCHED" },
      { "eventId": "c0d3e4...", "verifyStatus": "UNCONFIRMED" }
    ]
  }
}
```

**四类状态的判定依据**：

| 状态 | 条件 |
|---|---|
| `MATCHED` | 链上存在该 eventId，且链上摘要 == 本地 `SHA256(canonical_text)` |
| `MISMATCHED` | 链上存在，但摘要不同 |
| `UNCONFIRMED` | 本地有快照，链上无记录（任务未完成） |
| `UNREACHABLE` | 查询链超时或节点异常 |

`overall` 取值：全 `MATCHED` → `PASS`；含 `MISMATCHED` → `FAIL`；其余 → `PARTIAL`。

```json
{
```
