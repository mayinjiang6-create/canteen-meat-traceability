## 1 一句话结论

| 项 | 任务书写法 | 实测结果 | 处理 |
|---|---|---|---|
| 链 | FISCO BCOS 2.9 Air 四节点 | **3.17.0**，四节点在跑 | 按实际版本实现，论文如实写 |
| 群组 | `groupId = 1`（2.x 数字组） | **`groupId = "group0"`**（3.x 字符串组） | 全部接口改用 `group0` |
| 合约编译器 | Solidity 0.4.25 | 前端内置 **solcJ 0.8.11** | 合约已移植到 `^0.8.11` |
| 中间件 | WeBASE-Front + Sign | **WeBASE 3.1.1**，Front:5002 / Sign:5004 均已在跑 | 直接复用，无需安装 |
| 签名方式 | 统一演示账户 | Sign 外部签名，需 `appId` + `signUserId` | 已建 `meattrace / meattraceadmin` |
| 读接口 | `/trans/handle` 查询 | `query-transaction` 空指针 | **改用节点 web3 RPC `eth_call`**（已开启 8545） |

> 这不是"环境不对"，而是"环境比任务书新"。论文里要把版本写准，不能照抄任务书。

## 4 合约部署与写入（已验证通过）

### 4.1 编译

前端自带 solc 0.8.11，通过 `POST /WeBASE-Front/contract/contractCompile` 提交 base64 源码即可：

```json
{ "contractName": "TraceRegistry", "groupId": "group0", "solidityBase64": "<base64>" }
```

返回 `contractAbi`（字符串）与 `contractBin`。

### 4.2 部署

**注意两个坑**：

1. 必须用 `POST /contract/deployWithSign`，传 `signUserId`，**不要传 `user`**（传了会报 `user's privateKey is null`，因为它会去本地私钥库找）。
2. 成功时**不返回 JSON，直接返回纯文本合约地址**。

```json
{
  "groupId": "group0",
  "contractName": "TraceRegistry",
  "contractPath": "",
  "bytecodeBin": "<bin>",
  "abiInfo": [ /* ABI 数组 */ ],
  "funcParam": [],
  "signUserId": "meattraceadmin"
}
```

**结果**：

```
0xd24180cc0fef2f3e545de4f9aafc09345cd08903
```

### 4.3 写入存证

`POST /WeBASE-Front/trans/handleWithSign`

**首条真实交易**：

|---|---|
| eventId | `6f1c2b9a…0718` |
| batchId | `PB20261118001` |

### 4.4 幂等与冲突（已验证）

| 场景 | 交易 | 返回码 | 判定 |
|---|---|---|---|
| 同 eventId + 同摘要，再提交一次 | block 7 | **1** | `RESULT_DUPLICATE` 幂等 ✅ |
| 同 eventId + 异摘要（全 F） | block 8 | **2** | `RESULT_CONFLICT` 冲突、不覆盖 ✅ |

> 这三条是论文 6.2 节"幂等性证明"的核心证据，截图与交易哈希已留存。

### 4.5 `bizTime` 修正

文档早期写的 `1763429400` 是错的（对应 2025-11-18）。正确值：

```
2026-11-18 09:30:00 +08:00  →  1794965400
```

**摘要不受影响**：摘要计算用的是规范串里的 ISO-8601 文本，不是 Unix 秒。但合约参数必须传对。

## 5 已知缺陷：`query-transaction` 空指针

### 5.1 现象

```http
POST /WeBASE-Front/trans/query-transaction
```

无论传什么参数组合，一律返回：

```json
{"code":500,"errorMessage":null}
```

### 5.2 定位

```
java.lang.NullPointerException
  at com.webank.webase.front.transaction.TransService.getABIDefinition(TransService.java:582)
  at com.webank.webase.front.transaction.TransService.sendQueryTransaction(TransService.java:307)
```

### 5.3 已排除

| 假设 | 验证 | 结论 |
|---|---|---|
| ABI 里 `internalType` 让老解析器崩 | 去掉全部 `internalType` 重试 | 仍 500 |
| 多返回值（两个 string）导致解码失败 | 改调 `totalEvents()`（纯 uint256） | 仍 500 |
| 合约未存入 Front 库 | `POST /contract/save` 成功（id 5411）后重试 | 仍 500 |
| 需要 `userAddress` | 补 `userAddress` 重试 | 仍 500 |
| `encodeStr` 要带 `0x` | 带前缀重试 | 仍 500 |
| 旧版 ABI 格式（`constant`/`payable`） | 手工构造 legacy ABI 重试 | 仍 500 |

### 5.4 临时可用路径

`POST /trans/handleWithSign` 调用 view 函数能正确返回：

```json
// 调用 totalEvents() → 返回
["1"]
```

代价是**每次读都会产生一笔交易**（占块、耗时）。演示 6 条事件核验 = 6 笔交易，页面响应会被拖慢，且污染账本。

### 5.5 解决：改用节点标准 JSON-RPC 读链

**根因判断**：WeBASE-Front 3.1.1 的 `sendQueryTransaction` 在本版本存在缺陷，与本项目合约无关（已排除 ABI 格式、返回类型、合约入库、账户地址等六种假设）。

**解法**：FISCO BCOS 3.x 节点自带 **web3 RPC**（默认端口 8545，配置项在 `config.ini` 的 `[web3_rpc]`，默认 `enable=false`）。开启后即可用标准 Ethereum JSON-RPC 读链。

```bash
# 只改 node0，另外三节点保持运行，共识不受影响
cd /home/zym/fisco/nodes/127.0.0.1/node0
cp config.ini config.ini.bak.20261118
sed -i '/^\[web3_rpc\]/,/^\[cert\]/ s/^    enable=false/    enable=true/' config.ini
bash stop.sh && bash start.sh
```

**验证结果**：

```bash
curl -X POST http://192.168.239.130:8545 -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"eth_call","params":[{"to":"0xd241…8903",
       "data":"0xa3b61a9c6f1c…0718"},"latest"],"id":1}'
```

解得：

```json
{
  "batchId": "PB20261118001",
  "eventType": "ACCEPT_RESULT",
  "bizTime": 1794965400,
  "dataDigest": "16decfa5e4ccb17cc948c8d3b44c59439fcd7244e2280a0a6cf5a5f86bc770bf",
  "submitter": "0x0bd53242ca7ee7fb0ce57a3cb296b6d4b237dbe8",
  "createdAt": 1795000509666,
  "exists": true
}
```

与写入时的参数**逐字段一致**。回执查询同样可用：

```bash
eth_getTransactionReceipt 0xcf8c6e6f…
→ blockNumber 5, status 0x1, gasUsed 262488,
  from 0x0bD5…dbe8, to 0xd241…8903
```

### 5.6 最终读写分工

| 方向 | 通道 | 接口 | 理由 |
|---|---|---|---|
| **写**（存证 append） | WeBASE-Front + WeBASE-Sign | `POST /trans/handleWithSign` | 私钥由 Sign 托管，符合任务书"统一演示账户"要求 |
| **读**（query / exists） | 节点 web3 RPC | `POST :8545 eth_call` | 免交易、毫秒级、标准接口，不受 Front 缺陷影响 |
| **回执** | 节点 web3 RPC | `eth_getTransactionReceipt` | 直接拿 status / blockNumber / gasUsed |

这个分工比"全走 WeBASE"更合理：**写要有身份与签名，读只要数据**。读走轻量 RPC，公开溯源页才不会因为 6 条事件核验而拖慢。

> 论文第 5 章要写这一段。它不是"绕过问题"，而是"发现中间件缺陷后重新划分职责"——这种叙述在答辩里比"一切顺利"更有说服力。

### 5.7 另一个坑：`block.timestamp` 是毫秒

FISCO BCOS 3.x 的 `block.timestamp` 返回**毫秒**（实测 `1795000509666`），不是 2.x 的秒。后端写 `created_at` 时要除以 1000，否则会存成公元 5 万年。

## 7 复现命令

```bash
# 编译
python scripts/chain_tools.py compile

# 部署
python scripts/chain_tools.py deploy

# 写入
python scripts/chain_tools.py append <eventId> <batchId> <eventType> <bizTime> <digest>

# 校验（当前走 handleWithSign，见第 5 节）
python scripts/chain_tools.py info
```
