## 1 设计目标与边界

**目标**：为每个业务事件留下一条"写过就改不了"的记录，并能在任何时候用同一条记录证明链下数据没被动过。

**只做三件事**：

1. 追加事件（`append`）
2. 按事件标识查询（`query`）
3. 按批次查事件列表（`batchEventCount` / `batchEventAt`）

**明确不做**：

| 不做 | 原因 |
|---|---|
| 不在链上存业务明细（数量、检验结论、供应商名称） | 全量上链 5 年将达 GB 级，成本与查询延迟都不划算；存证的本质是"防篡改"而不是"存数据" |
| 不在链上做复杂业务校验（如数量是否够） | 链上 `require` 失败会消耗 gas 且难回滚业务，复杂状态应由后端维护 |
| 不支持修改与删除 | 溯源场景一旦允许改，存证价值归零；纠错靠追加"更正事件" |
| 不做权限矩阵 | 演示环境所有事件由统一账户提交，合约只保留 `owner` 用于部署管理 |

## 2 数据结构

```solidity
struct EventRecord {
    string  batchId;      // 业务批次号 PB*/PR*
    string  eventType;    // 9 类事件之一
    uint256 bizTime;      // 业务发生时间（Unix 秒）
    bytes32 dataDigest;   // 规范化快照的 SHA-256
    address submitter;    // 提交账户
    uint256 createdAt;    // 上链时间（block.timestamp）
    bool    exists;       // 存在标记（区分"空结构"与"已写入"）
}
```

**为什么存 `bizTime` 和 `createdAt` 两个时间**：

- `bizTime` 是业务实际发生的时间（可能补录，晚于上链）
- `createdAt` 是区块时间，不可伪造
- 两者差值本身就是审计线索：若某事件 `createdAt - bizTime` 异常大，说明是事后补录

**为什么 `exists` 单独一个布尔**：Solidity 的 `mapping` 对不存在的 key 返回全零结构，无法用 `dataDigest == 0` 区分"没写过"和"写了个空的"。显式标记是低成本的好习惯。

## 3 事件模型

```solidity
event EventAppended(
    bytes32 indexed eventId,
    bytes32 indexed batchKey,
    string  eventType,
    bytes32 dataDigest,
    address submitter,
    uint256 createdAt
);

event ConflictDetected(
    bytes32 indexed eventId,
    bytes32 existingDigest,
    bytes32 incomingDigest,
    address submitter
);
```

`ConflictDetected` **不是异常，是告警**。冲突时合约不 revert，而是记一条日志并返回 2。原因：revert 会让调用方拿不到原因，也可能被 WeBASE-Front 包装成通用错误；返回码 + 事件日志能让后端精准区分"业务重试"与"数据被篡改"。

## 4 接口签名与返回码

| 方法 | 签名 | 说明 |
|---|---|---|
| `append` | `(bytes32 eventId, string batchId, string eventType, uint256 bizTime, bytes32 dataDigest) returns (uint8)` | 追加事件 |
| `query` | `(bytes32 eventId) view returns (string, string, uint256, bytes32, address, uint256, bool)` | 单条查询 |
| `batchEventCount` | `(string batchId) view returns (uint256)` | 批次事件数 |
| `batchEventAt` | `(string batchId, uint256 index) view returns (bytes32)` | 按索引取事件标识 |
| `exists` | `(bytes32 eventId) view returns (bool)` | 是否存在 |
| `totalEvents` | `public uint256` | 累计事件数（运维指标） |

**`append` 返回码**：

| 码 | 常量 | 含义 | 后端处理 |
|---|---|---|---|
| 0 | `RESULT_APPENDED` | 新增成功 | 任务置 `CONFIRMED`，写回执 |
| 1 | `RESULT_DUPLICATE` | 同事件同摘要，幂等 | 任务置 `CONFIRMED`，**不重复记账** |
| 2 | `RESULT_CONFLICT` | 同事件不同摘要 | 任务置 `CONFLICT`，告警，**保留原记录** |

> 注意：返回码 0/1/2 都是"交易成功执行"（`tx_status = 0x0`），区别在合约内部逻辑。后端不能只看交易状态，必须解析 return 值。

## 5 摘要规范化规范（本项目最核心的一条规则）

摘要必须满足：**同样的业务内容，无论换台机器、换个 JVM、换种数据库排序，算出来必须一模一样。**

### 5.1 规范串格式

`canonical_text` 为 UTF-8 编码、`\n` 换行（LF）、**末尾不带换行**的纯文本，固定 8 行：

```
v1
eventId:{32 位 hex}
batchId:{批次号}
eventType:{事件类型}
bizTime:{ISO-8601 带偏移}
quantity:{定点 3 位小数}
unit:{小写单位}
payload:{规范化 JSON}
```

### 5.2 字段规则

| 字段 | 规则 | 反例（会导致摘要漂移） |
|---|---|---|
| `v1` | 规范版本号，**写死不可变**；规范变更必须升 `v2` 并双轨并存 | 直接改格式不升版本 → 历史事件全部误判不一致 |
| `eventId` | 32 位小写 hex，无 `0x` 前缀 | 混入大写、带 `0x` |
| `batchId` | 原样，不做大小写转换 | 一处转大写一处不转 |
| `eventType` | 枚举字面量，全大写 + 下划线 | `Accept_Result` |
| `bizTime` | `yyyy-MM-dd'T'HH:mm:ssXXX`，秒级，无毫秒，**固定 `+08:00`** | 用 `Date.toString()`、用 UTC、带毫秒 |
| `quantity` | `BigDecimal.setScale(3, HALF_UP)`，无千分位、无正号；负数为 `-1.500`；空值写 `0.000` | 用 `double`、`125.5` 与 `125.500` 混用 |
| `unit` | 小写，空值写 `kg` | `KG` / `Kg` |
| `payload` | 见 5.3 | — |

### 5.3 payload JSON 规范化

1. **键名按 ASCII 升序**排序（不是插入顺序，不是字母表顺序之外的任何顺序）
2. **无空格**：分隔符固定为 `,` 与 `:`，不输出缩进
3. **布尔**：`true` / `false`，不用 `1` / `0`
4. **数字**：统一输出为定点 3 位小数的裸数字（如 `3.500`），禁止科学计数法（`3.5E0`）
5. **字符串**：标准 JSON 转义，但**不转义非 ASCII 字符**（中文直出 UTF-8，不写成 `\u674e`）
6. **空值**：`null`，不输出空字符串
7. **数组**：保持业务语义顺序（如来源列表按 `purchaseBatchNo` 升序），不排序对象数组
8. **不输出**：`created_at`、`updated_at`、自增 `id`、任何数据库生成字段

> 第 8 条最容易被忽略：如果把自增 id 写进 payload，换一台机器重放数据，摘要必然不同。

### 5.4 计算与存储

```
digest_hex = SHA256(canonical_text.getBytes(UTF_8))   // 64 位小写 hex
on_chain   = bytes32(hexToBytes(digest_hex))          // 去掉 0x
```

## 6 幂等与冲突判定

| 场景 | 链上已有 | 新提交摘要 | 合约行为 | 返回码 | 后端任务状态 |
|---|---|---|---|---|---|
| 首次存证 | 无 | D1 | 写入 | 0 | `CONFIRMED` |
| 网络重试（最常见） | D1 | D1 | 不写，直接返回 | 1 | `CONFIRMED` |
| 内容被改过 | D1 | D2 | 不覆盖，记 `ConflictDetected` | 2 | `CONFLICT` |
| 事件标识撞车 | D1（另一业务） | D2 | 不覆盖，记 `ConflictDetected` | 2 | `CONFLICT` + 人工排查 |

**为什么冲突不覆盖**：如果允许覆盖，"改数据 → 重新上链"就成了一条完整的篡改路径，存证系统自己把门打开了。冲突必须留痕并交由人工判断，这是设计上的红线。

**幂等的两个层次**（会被追问）：

- **业务层幂等**：前端传 `requestId`，后端 24h 内同 `requestId` 直接返回首次结果，不产生新记录（BR-10）
- **存证层幂等**：合约层用 `eventId + dataDigest` 判重（BR-11）

两层缺一不可：只有业务层，前端重试换了个 `requestId` 就会重复上链；只有存证层，业务表已经多了一条脏数据。

## 7 合约源码

> 落地文件：`contract/TraceRegistry.sol`（唯一事实来源，改动以该文件为准）
> 编译器：solc **0.8.11**（WeBASE-Front 3.1.1 内置 `solcJ-0.8.11.0.jar`）

核心签名（完整实现见文件）：

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.11;

contract TraceRegistry {
    uint8 public constant RESULT_APPENDED = 0;   // 新增
    uint8 public constant RESULT_DUPLICATE = 1;  // 幂等
    uint8 public constant RESULT_CONFLICT  = 2;  // 冲突

    struct EventRecord {
        string  batchId;
        string  eventType;
        uint256 bizTime;
        bytes32 dataDigest;
        address submitter;
        uint256 createdAt;
        bool    exists;
    }

    address public owner;
    uint256 public totalEvents;

    function append(
        bytes32 eventId,
        string calldata batchId,
        string calldata eventType,
        uint256 bizTime,
        bytes32 dataDigest
    ) external returns (uint8);

    function query(bytes32 eventId) external view returns (
        string memory batchId, string memory eventType, uint256 bizTime,
        bytes32 dataDigest, address submitter, uint256 createdAt, bool exists);

    function batchEventCount(string calldata batchId) external view returns (uint256);
    function batchEventAt(string calldata batchId, uint256 index) external view returns (bytes32);
    function exists(bytes32 eventId) external view returns (bool);
}
```

**0.4.25 → 0.8.11 的改动点**（文档里可作为"版本适配"一段）：

| 项 | 0.4.25 写法 | 0.8.11 写法 |
|---|---|---|
| 版本声明 | `pragma solidity ^0.4.25;` | `pragma solidity ^0.8.11;` |
| 构造函数 | `constructor() public` | `constructor()` |
| 外部函数 | `public` | `external`（省 gas，语义更准） |
| 字符串参数 | `string batchId` | `string calldata batchId` |
| 返参动态类型 | `returns (string x)` | `returns (string memory x)` |
| 溢出检查 | 无（需 SafeMath） | 编译器内置，`totalEvents + 1` 自动检查 |
| 许可声明 | 无 | 需 `SPDX-License-Identifier` |

> 逻辑一行没改，只做了语法与可见性适配。这是移植而不是重写，摘要规范完全不受影响。

### 8.4 查询（读走标准 RPC）

WeBASE-Front 3.1.1 的 `/trans/query-transaction` 在 solc 0.8 ABI 下**必现空指针**（`TransService.getABIDefinition`），已排除六种假设，详见 `TECH-10` 第 5 节。

**解决办法**：开启节点的 web3 RPC（`config.ini` 的 `[web3_rpc] enable=true`，端口 8545），用标准 `eth_call` 读链。

```json
POST http://192.168.239.130:8545
{"jsonrpc":"2.0","method":"eth_call",
 "params":[{"to":"0xd24180cc0fef2f3e545de4f9aafc09345cd08903",
            "data":"0x<encodeStr>"},"latest"],"id":1}
```

`data` 由 WeBASE-Front 的 `/trans/encodeFunction` 生成（返回纯 hex，不带 0x）。返回结果为 ABI 编码的整体，按 `query()` 的 7 个返回值顺序解析：

| 偏移 | 字段 | 说明 |
|---|---|---|
| word 0 | batchId | 动态字符串，取偏移后读长度 |
| word 1 | eventType | 同上 |
| word 2 | bizTime | uint256，Unix 秒 |
| word 3 | dataDigest | bytes32 |
| word 4 | submitter | address（右 20 字节） |
| word 5 | createdAt | uint256，**毫秒**（3.x 特性） |
| word 6 | exists | bool |

**实测返回值**：

```json
{
  "batchId": "PB20261118001",
  "eventType": "ACCEPT_RESULT",
  "bizTime": 1794965400,
  "dataDigest": "16decfa5e4ccb17cc948c8d3b44c59439fcd7244e2280a0a6cf5a5f86bc770bf",
  "submitter": "0x0bd53242ca7ee7fb0ce57a3cb296b6d4b237dbe8",
  "createdAt": 1795000509666,
```

**读写分工**：写走 WeBASE-Front + Sign（私钥托管、有身份），读走节点 RPC（免交易、毫秒级）。回执用 `eth_getTransactionReceipt`。

## 9 核验流程（链上链下对照）

```
① 取 event_snapshot 的一行
② digest_recalc = SHA256(canonical_text)          ← 用库里的原文，不重新拼装
③ 读链上该 eventId 的 dataDigest
④ if 读链超时/异常              → UNREACHABLE
   if 链上无该事件               → UNCONFIRMED
   if 链上 digest == digest_recalc → MATCHED
   else                          → MISMATCHED
```

**核验只看摘要，不看业务字段**。因为链上本来就没存业务字段——这正是"链上存证、链下存源"的必然结果，也是评审要讲清楚的一点：**我们证明的是"这份记录自写入后未被修改"，而不是"这份记录的内容真实"**。后者需要检疫机构背书，那是制度问题不是技术问题。

## 10 安全与限制

| 项 | 现状 | 说明 |
|---|---|---|
| 重放攻击 | 不适用 | 存证类合约无资金转移，重放只会命中幂等分支 |
| 权限控制 | 全部写操作由统一演示账户签名 | 生产需接 RBAC + 多机构独立签名 |
| 私钥管理 | 由 WeBASE-Sign 托管 | 私钥不落业务库，不入 Git |
| 合约升级 | 不支持 | 溯源要求规则稳定；确需变更则部署新合约并双写过渡 |
| 链上数据公开 | 是 | 只存摘要，不泄露业务明细，属于可接受的设计 |
| Gas | 单次 append 实测 262,488 | 演示环境无 gas 费用压力 |
