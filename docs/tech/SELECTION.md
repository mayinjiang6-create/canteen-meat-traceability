## 1 为什么调 WeBASE-Front，而不引 `fisco-bcos-java-sdk`

**结论**：链写入走 WeBASE-Front 的 `POST /trans/handleWithSign`，链读取走节点 JSON-RPC `eth_call`，全程不引入 Java SDK。

**理由**：

1. 私有钥不进后端。签名交给 WeBASE-Sign 的外部账户（`meattracemeattraceadmin` → `0x0bd53242…dbe8`），
   后端只持 `appId` / `signUserId`，泄露了也签不出别的业务的交易。
2. 免装 SDK 就免掉一整类依赖冲突。`fisco-bcos-java-sdk` 与 Druid 在历史项目里出现过
   连接池 bean 初始化顺序问题，本项目改用 **HikariCP**（Spring Boot 默认，零额外依赖）彻底绕开。
3. HTTP 调用可观测。每个请求能抓包、能重放、能改成 curl 复现——排障成本远低于"SDK 内部报了个空指针"。

**代价**：多一个中间件（WeBASE 三件套 5001/5002/5004），部署清单里要写清版本与端口。

## 2 为什么链上读取改走节点 `eth_call`，而不用 WeBASE 的查询接口

这一条不是选型偏好，是**实测踩到的缺陷**。

**现象**：WeBASE-Front 3.1.1 的 `/trans/query-transaction` 在 solc 0.8 编译出的 ABI 下**必现 NPE**，
换成 0.6 的合约正常。追到根因是它对 `output` 字段做了隐式类型假设，0.8 的编码布局变化后取到 null。

**处置**：

| 路径 | 方案 | 结果 |
|---|---|---|
| 读 | 节点 JSON-RPC `eth_call`（:8545，node0 已开 `web3_rpc`） | ✅ 免交易、毫秒级、稳定 |
| 读（备选，已否决） | 用 `handleWithSign` 发一笔只读交易再解析回执 | ❌ 每读一次上链一笔，成本与延迟都不可接受 |
| 读（备选，已否决） | 降级 solc 到 0.6 迁就中间件 | ❌ 为绕中间件 bug 改合约版本，本末倒置 |

实测单次 `eth_call` 约 10.5 ms，是端到端耗时的主导项，但完全可接受。
完整证据见 `TECH-10` 第 5 节。

## 3 为什么链上只存 `eventId / batchId / dataDigest` 三要素

全量上链成本高、查询慢，而且业务字段天天变、链上结构一改就要重新部署合约。

**存证的本质是防篡改，不是存数据。** 只要能把"链下这条记录"和"链上这个摘要"一一对应起来，
改动任何一个字节都会让核验状态从 `MATCHED` 变成 `MISMATCHED`，目的就达到了。

**代价**：查明细必须回链下库，链上数据无法独立还原业务。
这在本项目里是可接受的——公开溯源页本来就是"链下读明细 + 链上读摘要 + 两边比对"的组合。

**摘要怎么算**：8 行规范串 → SHA-256，字段顺序与分隔符写死在 `TECH-04` 第 5 节，
并给了一个基准向量（`16decfa5…70bf`）用于回归——换实现、换语言都能对齐验证。

## 4 事件模型：只追加，不更新不删除

溯源要求不可否认（non-repudiation）。更新会抹掉历史，删除等于允许伪造者"撤回"。

**做法**：所有业务动作写一条新事件；状态流转体现在业务表上，事件表始终是 append-only。

**代价**：纠正错误不能改历史，只能追加一条新事件覆盖语义，业务侧必须处理"最新有效事件"。
这一点在召回与异常处置里体现得最明显——`REPORTED` 与 `CLOSED` 是两条独立事件。

---

## 5 存证异步化

上链耗时 100 ms ~ 2 s。同步做的话，采购提交接口会被链的抖动直接拖死。

**做法**：业务事务内只写"待提交任务"（同事务，保证不丢），由 `EvidenceWorker` 异步认领并上链。

**代价**：引入最终一致，必须做四类状态兜底：

| 状态 | 含义 |
|---|---|
| `MATCHED` | 链下摘要与链上一致 |
| `MISMATCHED` | 两边不一致（数据被改过） |
| `UNCONFIRMED` | 尚未上链或无法确认 |
| `UNREACHABLE` | 链不可达（熔断后置位） |

四类状态与「检验结论」**必须分栏展示**，不能合成一个"通过/不通过"——否则运维故障会被误读成食品安全问题。

## 6 业务编号：`biz_sequence` 发号器

**禁止 `SELECT MAX(id)+1`**。并发下必然撞号，而且撞号发生在最不该出错的地方（采购单号、验收单号）。

**做法**：单表 `biz_sequence`，用 `LAST_INSERT_ID(expr)` 原子自增，四类业务（供应商 / 采购 / 验收 / 加工）
统一由 `module.sequence.SequenceService` 发号。

**踩坑**：发号器必须放在 `module.*` 包下——`@MapperScan` 只扫 `module`，放外面启动就报 mapper 找不到。

---

## 7 向量检索：内存暴力余弦，不引向量数据库

知识库片段量级 < 1 万，暴力检索 < 50 ms；少一个中间件就少一个故障点，也让 `trusted-rag/` 保持零第三方依赖、
`pip install` 都不用跑。

**代价**：规模上千倍后需要换 HNSW。这一点在 `trusted-rag/README.md` 的已知限制里写明了。

**更重要的一个实测结论**：拿 `BGE-small-zh-v1.5` 替换词面检索后，答案正确率从 **1.00 掉到 0.9231**
（拒答仍 1.00），失败的 6 条全是检疫证号一类的精确查询。所以**保留词面检索**，
方向改为 BM25 + 向量混合。评价指标全文见 `trusted-rag/embedding_eval.json`。

> 这次实验的价值不在"上了向量"，在"证明了在这个语料上向量不该独挑大梁"。

---

## 8 连接池：HikariCP，不用 Druid

Druid 与 `fisco-bcos-java-sdk` 在历史项目里有冲突记录（bean 初始化顺序 / 监控切面干扰）。
本项目既然不引 SDK，理论上没这个约束了，但仍然选 HikariCP——Spring Boot 默认、零配置、指标够用。

**没有引入 Druid 的监控面板是明确取舍**：本项目链路的瓶颈在链，不在连接池，
为此多背一个中间件不划算。

## 9 演示拓扑：单机 4 节点

资源受限（虚拟机 2 核 8G），4 节点只为体现多节点共识，**不为容灾**。

**所以不能宣称高可用**。README 与 `TECH-08` 的性能一节都写了"这不是压测，不推断高并发能力"。
