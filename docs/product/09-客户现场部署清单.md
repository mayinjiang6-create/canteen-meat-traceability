## 0 一句话交付

```bash
cd deploy && cp .env.example .env && docker compose up -d --build
# 浏览器打开 http://<服务器IP>:8088 ，账号 admin / Admin@123
```

三个容器：`mysql`（数据）+ `backend`（业务与存证）+ `frontend`（页面与反代）。
**链是可选外部依赖**：不接链也能完整演示业务，公开溯源页会显示「暂无法核验」（`UNREACHABLE`），
不会把"没接链"误报成"数据被改"。

## 2 环境前置与端口表

### 2.1 前置条件

| 项 | 最低 | 推荐 | 校验命令 |
|---|---|---|---|
| CPU / 内存 | 2 核 / 4 GB | 4 核 / 8 GB | `nproc`、`free -h` |
| 磁盘 | 20 GB 可用 | 50 GB | `df -h` |
| Docker | 24.x | 最新稳定版 | `docker version` |
| Compose | v2.20 | 最新 | `docker compose version` |
| 网络 | 能拉基础镜像 | 配镜像加速 | `docker pull mysql:8.0` |
| 时区 | Asia/Shanghai | 同 | `timedatectl` |

> 首次构建需要访问 Maven 中央仓库与 npm 源。内网现场建议提前在有网机器上
> `docker compose build` 后用 `docker save` / `docker load` 搬运镜像。

### 2.2 端口表

| 服务 | 容器端口 | 宿主机默认 | 变量 | 是否需对外 |
|---|---|---|---|---|
| frontend | 80 | **8088** | `FRONTEND_PORT` | ✅ 客户只访问这个 |
| backend | 8080 | 8080 | `BACKEND_PORT` | 建议只对内网/本机 |
| mysql | 3306 | 3306 | `MYSQL_PORT` | ❌ 生产应关闭映射 |
| WeBASE-Front（可选） | 5002 | — | `WEBASE_BASE_URL` | 仅后端访问 |
| 链 RPC（可选） | 8545 | — | `CHAIN_RPC_URL` | 仅后端访问 |

> 生产交付建议把 `mysql` 与 `backend` 的 `ports` 注释掉，只保留 frontend，
> 由 Nginx 走容器网络访问后端。

## 3 三步启动

### 第 1 步：准备配置

```bash
cd deploy
cp .env.example .env
# 必改三项：MYSQL_ROOT_PASSWORD、DB_PASSWORD、JWT_SECRET（≥32 字节随机串）
vi .env
```

生成随机密钥（不要用示例值）：

```bash
openssl rand -base64 48
```

### 第 2 步：静态自检（10 秒，不用 Docker）

```bash
python check_deploy.py        # 需要 PyYAML；没有也能跑，会跳过 YAML 解析项
```

期望输出结尾：

```
结论：PASS 34 / FAIL 0
→ 静态一致性全部通过。构建与运行验证仍需在有 Docker 的机器上执行
```

### 第 3 步：构建并启动

```bash
docker compose up -d --build          # 首次约 3–8 分钟（拉镜像 + Maven/npm 依赖）
docker compose ps                     # 三个服务都应是 running / healthy
docker compose logs -f backend        # 看到 Flyway 迁移 + Started MeatTraceApplication 即可
```

打开 `http://<服务器IP>:8088`，用 `admin / Admin@123` 登录。
公开溯源页免登录：`http://<服务器IP>:8088/trace/PB20261118001`。

停止 / 重启 / 清空数据：

```bash
docker compose stop
docker compose restart backend
docker compose down            # 保留数据卷
docker compose down -v         # ⚠️ 连数据一起删，仅用于重装演示环境
```

## 4 环境变量与密钥注入

**所有配置只走环境变量，仓库里没有任何口令与密钥。** `.env` 已在 `.gitignore` 中。

| 变量 | 作用 | 默认 | 现场是否必改 |
|---|---|---|---|
| `FRONTEND_PORT` | 对外访问端口 | 8088 | 端口冲突时改 |
| `BACKEND_PORT` | 后端映射端口 | 8080 | 一般不用 |
| `MYSQL_PORT` | MySQL 映射端口 | 3306 | 生产建议不映射 |
| `MYSQL_ROOT_PASSWORD` | root 口令 | 示例值 | ✅ 必改 |
| `DB_USER` / `DB_PASSWORD` | 业务库账号 | `meat` / 示例值 | ✅ 必改口令 |
| `JWT_SECRET` | 令牌签名（HS256，≥32 字节） | 示例值 | ✅ 必改 |
| `NPM_REGISTRY` | 前端构建源 | 官方源 | 国内建议 `https://registry.npmmirror.com` |
| `EVIDENCE_WORKER_ENABLED` | 是否轮询上链 | `false` | 接链时设 `true` |
| `WEBASE_BASE_URL` | WeBASE-Front 地址 | 虚拟机地址 | 接链时改 |
| `CHAIN_RPC_URL` | 节点 RPC（读路径） | 虚拟机地址 | 接链时改 |
| `CONTRACT_ADDRESS` | 合约地址 | 演示地址 | 换合约时改 |

密钥管理三条硬要求：

1. `.env` 权限收到 `chmod 600`，不进 Git、不进群聊、不写进交付文档
2. 交付完成后由客户方改一次口令，实施人员不再保留
3. 需要轮换 `JWT_SECRET` 时，全部已签发 token 立即失效（用户重新登录即可，无数据影响）

## 5 链可选接入与离线降级

### 5.1 两种交付形态

| 形态 | 配置 | 效果 |
|---|---|---|
| **纯业务**（默认） | `EVIDENCE_WORKER_ENABLED=false` | 业务全流程可用；事件停在"待存证"；公开页核验状态 `UNREACHABLE` |
| **含链** | `EVIDENCE_WORKER_ENABLED=true` + 三链参数 | 写入走 WeBASE-Front 签名交易，读走节点 `eth_call`；核验状态可到 `MATCHED` |

### 5.2 接入已有链

1. 确认后端容器能访问链：`docker compose exec backend curl -s http://<链IP>:8545 -X POST -H "Content-Type: application/json" -d '{"jsonrpc":"2.0","method":"eth_blockNumber","params":[],"id":1}'`
2. 改 `.env` 的 `WEBASE_BASE_URL` / `CHAIN_RPC_URL` / `CONTRACT_ADDRESS` / `EVIDENCE_WORKER_ENABLED=true`
3. `docker compose up -d backend` 重建
4. 打开公开溯源页，核验状态应从黄色 `UNREACHABLE` 变为绿色 `MATCHED`

> **不要把 FISCO 四节点 + WeBASE 塞进这个 compose**：链是独立基础设施，
> 客户环境里通常已有或在另一台机器上。合在一起会让升级、备份、故障定位全部耦合。

### 5.3 降级行为（已实测）

链不可达时的真实返回（本机实测，见第 8 节验收记录）：

```json
{"matched":0,"mismatched":0,"unconfirmed":0,"unreachable":1,"overall":"PARTIAL"}
```

页面显示黄色「暂无法核验」，**不是报错、不是白屏、不是"数据造假"**。
读路径有 5s 超时熔断，一次请求最多等一次超时，不会堆积。

## 6 数据初始化与备份恢复

### 6.1 初始化

后端启动时 Flyway 自动执行 `db/migration/V1~V6`：

| 脚本 | 作用 |
|---|---|
| V1 / V2 | 建表（16 张）+ 补表 |
| V3 | 演示数据（3 供应商 / 4 采购 / 3 加工 / 4 销售 / 1 冷链闭环） |
| V4 / V5 | 数量修正 + 请求幂等表 |
| V6 | `biz_sequence` 发号器 |

首次启动看到 `Successfully applied 6 migrations` 即完成。
**不要手工改表结构**：Flyway 校验和不匹配会让后端拒绝启动（`clean-on-validation-error: false` 是有意的——宁可启动失败，也不清库）。

### 6.2 备份

```bash
# 全库备份（在宿主机执行，落到当前目录）
docker compose exec -T mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers meat_trace' > meat_trace_$(date +%Y%m%d_%H%M).sql

# 数据卷冷备（停服后打 tar）
docker compose stop backend
docker run --rm -v meat-trace_mysql-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/mysql-data-$(date +%Y%m%d).tar.gz -C /data .
docker compose start backend
```

### 6.3 恢复

```bash
docker compose stop backend
docker compose exec -T mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" meat_trace' < meat_trace_20261119_1600.sql
docker compose start backend
```

> 恢复后必须验证：登录成功 + 公开溯源 `PB20261118001` 能出时间线 + 核验状态与备份前一致。
> 备份只覆盖 MySQL；链上摘要不可回滚（这正是存证的价值），换库后可能出现 `MISMATCHED`，
> 属于预期现象，需在验收记录里写明。

## 7 升级与回滚

### 7.1 升级（向前）

```bash
cd deploy
docker compose pull          # 若用远程镜像
docker compose build --pull  # 本地构建最新代码
docker compose up -d         # 只重建有变化的容器
docker compose logs -f backend | grep -i flyway
```

Flyway 只会向前迁移，**不会自动降级**。

### 7.2 回滚

| 场景 | 做法 |
|---|---|
| 只回滚应用（库结构未变） | `git checkout <上一个版本tag>` → `docker compose up -d --build` |
| 库结构已变 | 先 `down`，恢复 §6.3 的 dump，再起旧版本镜像 |
| 单服务回滚 | `docker compose up -d --no-deps backend` 只重建后端 |

回滚窗口建议：升级前必备份（§6.2），并在验收单上写明版本号。

## 9 常见故障排查

### 9.1 定位三件套

```bash
docker compose ps                       # 谁没起来
docker compose logs --tail=200 backend  # 后端为什么没起来
docker compose logs --tail=100 mysql    # 库是否初始化完成
```

后端日志格式：`时间 级别 [traceId] 类名 - 消息`。
**每个接口响应都带 `traceId`**，把它贴给开发即可定位到具体请求。

### 9.2 故障对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `backend` 反复重启，日志有 `FlywayValidateException` | 数据库被手工改过 / 用了旧库 | 备份后重建库（§6.2→`down -v`→up），不要改校验和 |
| 日志 `Communications link failure` | MySQL 未就绪或口令错 | `docker compose ps` 看 mysql 是否 healthy；核对 `.env` 的 `DB_PASSWORD` |
| `Access denied for user 'meat'` | 卷里已存在旧的用户/口令 | 旧数据卷不会重新执行初始化脚本，改 `.env` 后需 `down -v` 或手工改授权 |
| 页面 502 Bad Gateway | 后端没起来 / 端口不对 | `docker compose logs backend`；确认 nginx 反代目标是 `backend:8080` |
| 页面打开是空白 + 控制台 404 | 静态文件没构建成功 | `docker compose build frontend` 看 npm/vue-tsc 报错 |
| 刷新 `/trace/xxx` 404 | 反代没加载 `nginx.conf` | 确认 `frontend/nginx.conf` 被 COPY 到 `/etc/nginx/conf.d/default.conf` |
| 核验状态长期黄色 `UNREACHABLE` | 未接链 / 链不可达 / 合约地址错 | 先在 backend 容器里 `curl` 节点 8545；再核对 `CONTRACT_ADDRESS` |
| 核验状态红色 `MISMATCHED` | 本地记录被改过，或换了库没换链 | **这是系统的正确行为**，不要"修复"成绿色；按 §6.3 恢复数据 |
| 端口被占用 `bind: address already in use` | 宿主机已有同端口服务 | 改 `.env` 的 `FRONTEND_PORT`，`docker compose up -d` |
| 中文乱码 / 时间差 8 小时 | 容器时区或字符集 | 确认 `TZ=Asia/Shanghai`；库用 `utf8mb4`；JDBC 串已带 `serverTimezone` |
| 构建卡在 npm | 内网无法访问官方源 | `NPM_REGISTRY=https://registry.npmmirror.com` 后重建 |
| `docker compose` 命令不存在 | 只装了 docker-compose v1 | 升级到 Compose v2（`docker compose version` 应带 v2） |

### 9.3 五分钟自愈顺序

1. `docker compose restart backend`（最常见：库启动慢导致首次连接失败）
2. `docker compose up -d --force-recreate backend`
3. `docker compose logs --tail=200 backend` 找到第一条 ERROR
4. 仍不通 → 按 §6.2 备份，`down -v` 重建演示环境，再导入备份
