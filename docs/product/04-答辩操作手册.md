## 2 15 分钟演示脚本

### 0:00–1:30 开场（不要念 PPT）

> "我的题目是高校食堂肉类供应链溯源系统。我先说清楚我要解决什么：食堂采购的肉来自多个供应商、多个批次，现在的台账能记录，但没法证明**记录事后没被改过**。我做的是：用批次把采购到餐桌串起来，把关键事件算成摘要上链，任何人扫码都能自己核一遍。"

**三句话定调**：问题（记录不可核）→ 做法（批次 + 事件摘要上链）→ 结果（扫码可自查，四类核验状态）。

### 1:30–4:00 正常流程：采购 + 验收

| 动作 | 画面 | 讲解要点 |
|---|---|---|
| 打开供应商管理 | 三家供应商列表 | "黑名单这家，系统会拒绝给他建采购单" |
| 新建采购批次 | 表单填写 | 重点说：**检疫证号、屠宰批次号、到货温度**这三个字段为什么必须录 |
| 提交 | 返回 `PB20261118001` | "注意这里返回的存证状态是 PENDING，业务已经成功，存证在后台异步进行——这个设计后面会讲" |
| 入库验收 | 判定合格 | "验收结果直接决定这个批次能不能进厨房" |

### 4:00–7:00 核心亮点：多来源加工

| 动作 | 讲解要点 |
|---|---|
| 打开加工投料 | "一个加工批次可能同时用两个采购批次的肉，这是真实食堂的常态" |
| 填两个来源 80 + 40，产出 120 | "系统在**同一个数据库事务**里做四件事：校验来源状态、校验不重复、校验余量够不够、扣减可用量" |
| 故意把投入改成 200 | 弹出「可用余量不足，剩余 40.000」| "这就是数量约束，不是提示，是拦截" |
| 改回正确值提交 | 成功，显示来源明细 |

**这里要停一下讲一句**：

> "多来源这件事，如果只存一个'用了猪肉 120 斤'，出了问题是查不到哪一批的。我建了 `source_relation` 表，每个来源批次投了多少都记下来，而且总量受可用量约束——这是这个系统在数据建模上最关键的一张表。"

### 7:00–9:00 异常：召回

| 动作 | 讲解要点 |
|---|---|
| 销售 25kg | 正常销售 |
| 触发召回 | 填原因"同批次抽检兽药残留超标" |
| 看结果 | 加工批次变 `RECALLED`，销售记录批量变 `RECALLED` |
| 再试着卖 | 被拒绝 | "召回之后这个批次任何渠道都卖不了了" |
| 打开公开页 | 时间线出现「已召回」节点 | "消费者也能看到，这是对外的交代" |

### 9:00–11:30 公开溯源：四类核验（**全场最重要**）

| 动作 | 讲解要点 |
|---|---|
| 手机扫码 / 输码 | 时间线 6 条事件，每条一个绿色徽标 |
| 讲徽标含义 | "绿 = 记录一致：我把链下这条记录的原文重新算一遍 SHA-256，和链上的比，一样。" |
| 演示不一致 | 用测试数据把某条记录改一个字段，刷新 → 红色「记录不一致」+ 顶部红色警示条 |
| 演示不可达 | 停掉一个节点再查 → 黄色「暂无法核验」 |
| **重点说这段** | "这里我要特别说明：**核验状态说明的是记录有没有被改，不是说明肉合不合格**。肉合不合格看的是旁边的检验结论，那是检疫机构给的。这两件事我强制分两栏展示，绝不合并——因为把'区块链已验证'说成'可以放心吃'，是不诚实的。" |

> 这一段说完，评委通常会点头。它证明你想清楚了技术的边界。

### 11:30–13:00 存证管理 + 链上记录

| 动作 | 讲解要点 |
|---|---|
| 存证任务列表 | 状态分布：已确认 / 待提交 / 不可达 |
| 点开一条 | txHash、区块高度、提交账户 |
| 展示幂等 | "同一条事件我重复提交一次，链上记录数不变，合约返回的是 1 而不是 0——这是幂等分支" |
| 展示冲突 | "如果同 eventId 但内容不同，合约返回 2 并记一条告警日志，**不覆盖原记录**。允许覆盖就等于给篡改开门。" |

### 13:00–14:00 问答模块（加分项）

| 动作 | 讲解要点 |
|---|---|
| 问"PB20261118001 这批猪肉的检疫结论是什么" | 答案 + 下方引用卡片 |
| 点引用 | 跳到对应事件 |
| 问一个知识库没有的 | 回答「未在已核验记录中找到依据」| "它不会编。而且我只喂已核验一致的事件，核验不一致的批次根本不进知识库——我只回答我能证明的部分。" |

### 14:00–15:00 收尾

> "总结三句：第一，我把多来源批次关系建成了可约束的数据模型；第二，我用事件摘要把链上链下对应起来，做出了四类可区分的核验状态；第三，我把这套东西完整交付了——源码、合约、迁移脚本、30 项测试、部署文档，任何人都能复现。谢谢老师。"

## 3 关键话术

### 3.1 一句话讲清"存证"

> "我不是把数据放到链上，我是把数据的指纹放到链上。指纹变了，说明数据被改过。"

### 3.2 一句话讲清"为什么不多上链"

> "全量上链五年要 GB 级空间，换来的只是省一次数据库查询。存证要的是防篡改，不是异地备份。"

### 3.3 一句话讲清"多来源"

> "一批肉可能来自三个养殖场。只记总量，出了问题谁都查不清。"

### 3.4 一句话讲清"AI 那部分"

> "区块链保证数据没被改，问答保证答案有出处。两者都在解决'凭什么信你'。"

## 4 高频问题与答案

**Q1 为什么用联盟链，不用公有链？**
食堂、供应商、监管部门是确定的几方，需要准入控制，公有链谁都能写反而没法管。而且联盟链不出币、无 gas 成本，适合这种内部协同场景。

**Q2 链上为什么只存摘要？**
三个原因：成本（全量上链五年 GB 级）、隐私（供应商信息不该公开）、性能（链上查询比数据库慢一到两个数量级）。摘要足够回答"数据有没有被改"这个问题。

**Q3 摘要怎么保证不同机器算出来一样？**
固定 8 行规范串：版本号、事件标识、批次、类型、ISO-8601 带时区的时间、定点 3 位小数的数量、单位、键名升序且无空格的 JSON。有一组基准测试向量写死在单元测试里，规范化逻辑一改测试就红。

**Q4 数据上链了，但源头录入时就是假的怎么办？**（**最容易被问，必须答好**）
这是这个技术方案的能力边界，我不回避。上链解决的是"写入之后不可篡改"，不解决"写入之前是否真实"。要解决源头真实性，需要检疫机构签发的电子证照、供应商资质核验、监管抽查这些制度手段。我的系统做的是**事后追责的抓手**：一旦出问题，能确定哪一批、哪个环节、谁录的、什么时候录的，而且这些记录改不了。

**Q5 四类核验状态怎么判定的？**
链上有记录且摘要相同 → 一致；链上有但摘要不同 → 不一致；链上无记录 → 尚未确认；查询超时 → 不可达。第四类是必须单独分出来的，不然链挂了会被误读成"数据造假"。

**Q6 为什么用 WeBASE-Front，不直接用 Java SDK？**
SDK 与连接池有版本冲突的历史问题，而且 SDK 升级会牵动整个后端依赖树。走 HTTP 前置服务，后端只依赖 HTTP 客户端，合约升级只要换 ABI，不用重新编译。

**Q7 幂等怎么做的？**
两层。业务层用 `X-Request-Id`，24 小时内同 ID 直接返回首次结果；存证层用合约里的 `eventId + 摘要` 判重，相同返回 1，不同返回 2 并告警、不覆盖。只有一层都不够：只有业务层，换个 ID 就重复上链；只有存证层，业务表已经多了脏数据。

**Q8 并发下怎么保证不超卖？**
不做 `SELECT FOR UPDATE`，用带条件的更新：`UPDATE ... SET available_qty = available_qty - ? WHERE id = ? AND available_qty >= ?`，看受影响行数，是 0 就回滚整个事务。这样没有行锁等待，也不会有幻读问题。

**Q9 四个节点有什么意义？能防什么？**
能防单点篡改：改一个节点的账本，其他三个节点的共识结果不认。演示环境是单机四节点，只能证明"共识机制生效"，不能证明"机房级容灾"——这两件事我在论文里分得很清楚。

**Q10 你的创新点是什么？**
不敢说创新，说三个具体做法：一是把"多来源加工"建成了带数量约束的关系模型，而不是记一个总数；二是把摘要规范化写成了带版本号和基准向量的规范，不是随手拼字符串；三是把核验状态拆成四类，并且和检验结论强制分栏。这三点都是工程判断，不是技术创新。

**Q11 系统还有什么不足？**
三条：温度数据是人工录入的，没有接传感器；四节点在一台机器上，不构成真正的多机构部署；供应商端目前是只读的，没有做多主体独立签名。这三条都在论文第七章写了后续工作。

**Q12 为什么加一个 AI 问答？跟溯源什么关系？**
因为溯源解决"数据可信"，但用户看不懂一堆表。问答让人能直接问"这批肉的检疫结论是什么"，而每个答案必须回引到具体事件 ID——引用能点开、能核验。**区块链保证数据没被改，问答保证答案有出处**，本质上都在解决可信问题。而且我只喂已核验一致的事件，核验不一致的批次不进知识库。

## 5 翻车预案

| 情况 | 现场反应 | 技术动作 |
|---|---|---|
| 链查不通，页面全黄「暂无法核验」 | **不要慌，这是设计的一部分**："正好给老师演示第四类状态——链不可达时系统不会假装通过，而是明确告诉你核不了。" | 不要重启，等 30 秒再看 |
| 后端 502 | "稍等，我切到刚才的录屏" | 播放录像对应片段 |
| 数据被清空 | "我重新导一下演示数据" | `mysql < V2__seed.sql`，30 秒 |
| 投屏失败 | 直接讲架构图与数据库设计 | 论文里的图也能撑 5 分钟 |
| 老师打断问细节 | 停下来答，答完问"我继续往下演示还是展开这块" | — |

> 通用原则：**任何故障都先归类到"四类核验状态"或"错误码"里解释**。系统对失败是有设计的，这比"运行正常"更能说明你做得认真。
