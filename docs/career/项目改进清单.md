## 4 别做的"改进"（投入产出比低）

| ❌ 别急着做 | 原因 |
|---|---|
| 整包迁到 Dify / LangChain | 会把最能讲清楚的"数据门槛 + 拒答纪律"变成平台配置，面试反而说不清 |
| 训一个小模型 | 没有数据量和算力，且 HR 不认；不如把检索和评测做扎实 |
| 加向量数据库 | 190 片段暴力余弦 0.45 ms，加 Milvus 是纯负担 |
| 把静态演示页堆成完整前端 | 招聘方看的是项目能力，不是 UI 精细度 |
| 为"显得 AI"硬塞 Agent | 任务书没有、场景也不需要，追问必露 |

## 5 建议的执行顺序（如果你只有一周）

1. **第 1 天**：发布可交互 API（第 3 项）→ 简历里的 Demo 立刻从"看图"变"能问"
2. **第 2–3 天**：接本地 embedding + 评测集扩到 50 条（第 1、2 项）→ 拿前后对比数字
3. **第 4 天**：查询改写 + 实体消歧（第 4、5 项）→ 修掉 README 里已写出的失败案例
4. **第 5 天**：可观测 + Docker 实测（第 7、8 项）→ 补齐交付岗最看重的运维证据
5. **第 6–7 天**：更新简历 bullet（只加数字，不重写）、准备 12 条面试追问

> 关键原则：**每改一项，就重跑一次评测并更新 `evaluation.json`。**
> 换检索器 / 改 Prompt 不改评测集，等于没测——这句话本身就是很好的面试答案。
