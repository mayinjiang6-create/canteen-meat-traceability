# 这个项目够用吗？没接 LLM 会不会只是 Demo

> 文档编号：CAREER-05 ｜ 版本：v1.0 ｜ 2026-11-19
> 结论先放这里：**它是 Demo，但对你目标岗位够用；"没接 LLM"这个短板已经补成可插拔生成层。**

---

## 1 先直接回答

**是不是 Demo？是。** 离线快照、不写真实 MySQL、不上链、没有用户系统、没有生产部署。
面试被问到时**直接承认**，别装成上线系统——装了一定会被追问穿。

**但 Demo 分两种**，招聘方分辨得出：

| | 玩具 Demo | 你现在这个 |
|---|---|---|
| 数据 | 假数据 / 几篇上传文档 | 186 条真实业务事件 + 完整业务表快照 |
| 功能 | 一个聊天框 | 10 个业务模块可真实操作、跨模块联动 |
| AI | 调一次 API，把结果贴出来 | 11 个工具、确定性工作流、可见轨迹、答案附依据、拒答纪律 |
| 可验证 | 截图 | 40 条评测 + v1/v2 前后对比 + 51 项核心断言 + 12 项浏览器交互 |
| 失败处理 | 没有 | 熔断、四类核验、LLM 失败自动回退 |
| 文档 | 一个 README | 20+ 份设计/部署/测试/交付文档 |

**对 AI 交付 / 实施 / 解决方案 / 产品岗，后面这一列比"接了个大模型 API 的聊天页"值钱得多。**
这些岗位招的是"能把 AI 落到有业务约束的系统里、讲得清边界、交付得了、出了问题能排"的人，
不是招"会调 `chat.completions`"的人。

## 2 分岗位看够不够

| 目标岗位 | 判断 | 理由 | 真正还缺的 |
|---|---|---|---|
| **AI 交付 / 实施 (FDE)** | ✅ **够，偏强** | 完整业务闭环、真实数据、状态机、评测、故障自愈、交付文档、可控 Agent | 真实客户现场数据、K8s/等保合规经验 |
| **AI 解决方案 / 售前** | ✅ **够** | 方案表达、PoC 可演示、边界清晰、指标可汇报、选型取舍讲得明白 | 行业案例、成本模型、标书经验 |
| **AI 产品（应届）** | ✅ **基本够** | 需求边界、四类状态设计、验收标准、拒答作为产品红线 | 用户调研、埋点与转化率 |
| **AI 应用开发（偏工程）** | ✅ **够** | 前后端 + 检索链路 + 工具编排都自己写、可复现 | 框架熟练度（LangChain/Dify）可补 |
| **大模型算法 / 研发** | ❌ **不够** | 没有训练、微调、embedding 实测、公开基准评测 | 模型、数据集、实验、论文/竞赛 |

> 你的目标岗位写的是前四类。按这个口径，**够用**。
> 只有投算法岗才需要推倒重来——那是另一个方向，不是这个项目的问题。

## 3 "没接 LLM"这件事，现在怎么答

**之前**：确实没接，是被问必露的短板。

**现在**：生成层做成了**可插拔适配器**：

- 软件里新增「LLM 接入设置」，填自己的 Base URL / Key / Model 即可启用（OpenAI 兼容接口）
- 已实测浏览器从本地页面直连服务商可行：预检 `200`、放行 `authorization` 头、
  `file://` 的 `Origin: null` 被接受，**不需要代理、不需要后端**
- 密钥只存本机浏览器，不进仓库、不上传；默认关闭；调用失败/超时/欠费**自动回退**到确定性模板
- 验证：核心 `51 项全过`（含 LLM 成功 / 拒答不调用 / 失败回退 / 清除密钥），
  浏览器 `12 项全过`（含 mock LLM 增强路径真实走通）

**最关键的设计取舍**（这才是面试里值钱的一句）：

> 「我刻意**没让模型决定调哪个工具**。工具选择、意图路由、护栏、引用校验全由代码决定，
> LLM 只把已经取到的工具结果组织成自然语言，不能新增事实。
> 因为交付型 Agent 里，**可控、可复现、成本可估**比"看起来更自主"重要；
> 而且这样断网、欠费、换模型都不会改变系统行为。」

这句话把"没接/轻接 LLM"从**缺陷**讲成了**架构决策**。

## 4 面试高频追问 · 标准答法

| 追问 | 怎么答 |
|---|---|
| 你的 LLM 在哪？ | 生成层是可插拔适配器，默认离线确定性编排保证可复现；有 Key 时接 LLM 只做语言组织，工具与护栏不交给模型。现场可以切给你看。 |
| 是不是只是个 Demo？ | 是，我主动说明：离线快照、不写库不上链、无用户系统。但它有真实数据、完整业务规则、可复现评测和交付文档，是工程 Demo 不是玩具 Demo。 |
| 为什么不用 LangChain / Dify？ | 这个场景约束强、工具固定、要可控可复现；框架能串链路但不替我守业务红线。简单低代码场景我会选 Dify，复杂编排会选 LangChain，取舍写在仓库里。 |
| 数据是真的吗？ | 来自本机 MySQL 的真实运行快照（26 供应商 / 71 采购 / 186 存证事件），逐条经链上摘要核验；演示里的新增操作只改浏览器本地状态，这点我也标了。 |
| 怎么证明 AI 有效？ | 40 条评测集含 14 条应拒答，拒答正确率 100%；保留 v1 baseline 做前后对比（0.71 → 1.00）；每条答案附 `[Tn]` 工具依据，可展开看原始结果。 |
| 为什么答案有些像模板？ | 离线模式是抽取式呈现，不是 LLM 生成；README 里写明这是边界。启用 LLM 后是自然语言，但依据和护栏不变。 |
| 如果重来怎么做？ | 一开始就该把生成层做成适配器；读路径先做接口探测再定方案；把 AI 模块提前纳入排期而不是留成可砍项。 |

## 6 真实 LLM 调用实测（2026-11-19）

不是 mock：真实浏览器打开软件 → 真实调用 DeepSeek OpenAI 兼容接口 → 真实生成答案。

| 项 | 实测 |
|---|---|
| HTTP | `200` |
| 请求模型 | `deepseek-chat` |
| 问题 | 哪些批次冷链温度超限？涉及哪些供应商？是否需要召回？ |
| 执行模式 | 确定性工作流 · 4 步 |
| 调用工具 | `list_cold_exceeded` → `get_purchase` → `list_recalls` → `get_rule` |
| Token | prompt 1315 / completion 505 / 合计 1820 |
| 页面徽标 | `LLM 增强模式` |
| 答案 | 结构化列出 4 条超限记录，逐条带 `[T1]…[T4]` 依据 |

**证据**（均不含密钥、不含 Authorization 头）：

- `app/evaluation_llm_real.json`：含 LLM 答案、离线确定性版本答案（可对照）、
  轨迹步数、工具清单、token 用量、HTTP 状态
- `screenshots/03-智能体真实LLM调用.png`：完整页面截图（轨迹 + 绿色答案框）
- `app/capture_llm_real.mjs`：可复现脚本，密钥从环境变量读取
- `app/verify_local.mjs`：本机已接入版验证（mock，不花钱）

**没有录视频**——但 `capture_llm_real.mjs` 可以随时现场重跑一次，
比一段录屏更能证明它是真算的；面试时直接点一下「运行智能体」即可。

> 实测驱动的一处改进：最初只把「前 3 行工具明细」喂给模型，
> 它诚实地指出「观察说命中 4 条、明细只有 3 条，第 4 条未找到依据」。
> 这不是模型错，是传参没说清。已在 Prompt 里标注「以下是样例行、
> 命中 N 条是完整数量」并加第 6 条规则，重跑后答案干净。
> 这段「发现问题 → 定位 → 修 → 重测」本身就是很好的面试素材。

**另一处被实测出来的短板**：用户现场输入「计算一下所有批次的肉类有多少斤」，
旧版因为固定关键词路由直接拒答「未匹配到可用工具」。已重构为三层覆盖：
确定性路由 → 代码精确汇总工具 `compute_stats` → 匹配不到时由 LLM 从 11 个白名单
工具里做规划（代码执行、参数校验、失败回退，越界护栏不交给模型）。
真实模型上自由提问「给我一份业务整体概览」被规划成 4 步并生成带依据的概览，
证据 `app/evaluation_llm_planner.json`。复验：核心 63/0、浏览器 14/0、本机版 4/0。

## 7 一句话结论

> **对你要投的岗位，它够用，而且比大多数"接了 API 的玩具 Demo"更能打。**
> 它仍然是 Demo——但那是 demo 的形态，不是能力的上限。
> 面试时主动把边界讲清楚、把「为什么 LLM 只做语言组织」讲成取舍，
> 比含糊地说"做了个 AI 系统"稳得多。
