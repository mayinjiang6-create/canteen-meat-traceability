# RAG 框架选型对照：手写 / LangChain / Dify

> 文档编号：CAREER-03 ｜ 版本：v1.0 ｜ 2026-11-19
> 用途：把「没用主流框架」从短板讲成有依据的取舍；面试被追问时的标准答案
> 参考：GitHub 上 Dify 官方 README 的功能对比与自托管资源要求（2026-11 检索）

---

## 0 先看结论

**没有"最好"，只有"现场条件 + 约束要求"下的最合适。**

| 场景 | 推荐 | 理由 |
|---|---|---|
| 客户现场只有一台机器、一个端口，要零成本可复现 | ✅ **手写标准库**（本项目） | 无数据库、无向量库、无框架依赖，190 片段内存检索够用 |
| 业务方要可视化编排 Prompt / 知识库，团队要协作运营 | ✅ **Dify** | 自带 RAG 引擎、Prompt IDE、可观测、Agent，AP I 可直接集成 |
| 编排逻辑复杂、要深度定制检索与多轮策略 | ✅ **LangChain** | 代码库灵活，组件可换；但要自己补可观测和评测 |

> 一句话：**Dify 是"平台"，LangChain 是"零件库"，手写是"在特定约束下只造需要的那一个零件"。**
> 本项目属于第三种，但把前两种最缺的「数据门槛 + 拒答纪律」做成了代码约束。

## 1 三方案逐项对照（基于真实功能对比）

| 维度 | 手写（本项目） | LangChain | Dify |
|---|---|---|---|
| 编程方式 | Python 标准库 | Python 代码 | API + 可视化界面 |
| 内置 RAG 引擎 | ❌ 自己写 | ❌ 组件拼 | ✅ 内置 |
| Prompt IDE | ❌ | ❌ | ✅ 可视化、可协作 |
| 可观测 / 日志 | ✅ 自建 traceId + 引用日志 | ⚠️ 需自己接 | ✅ 内置 |
| 多模型切换 | ✅ 适配器一行换 | ✅ 支持丰富 | ✅ 支持丰富 |
| 本地部署 | ✅ 单进程/单端口 | ✅ 代码即部署 | ✅ docker compose（多容器） |
| 最低资源 | 极低（无额外服务） | 低（Python 进程） | **2 核 / 4 GB 起**，多容器 + 向量库 |
| 评测可复现 | ✅ `python demo.py` 出 JSON | ⚠️ 需自建 | ⚠️ 平台内手动跑 |
| 幻觉治理 | ✅ 四类拦截 + grounded 三重 + 覆盖性校验 | ⚠️ 需自己写 | ⚠️ Prompt 约束为主 |
| 适合 | 强可信约束 / 资源受限 / 要讲清每一环 | 快速拼装复杂链路 | 低代码交付、客户自助运营 |

## 2 同场景怎么搭（面试能说出步骤即可）

### 2.1 用 Dify 搭（不实际部署，本机资源不够）

```
1. docker compose up -d 起 Dify（2 核 4G 起，多容器）
2. 知识库 → 导入 data/events.json 渲染后的 190 条自然语言片段
3. 在 Prompt IDE 里写规则：每个结论带 [n]、无依据拒答、不判定食品安全
4. 应用编排 → 知识库检索 + LLM → 发布为 API
5. 业务系统通过 API 调用
```

**本机为什么没做**：虚拟机 2 核 8 GB 看着够，但根分区 9.8 GB、**只剩 2.9 GB**，而 Dify
compose 会拉多个镜像 + 向量库；LVM 还有 8.22 GB 可扩，扩完才能跑。
这是资源取舍，不是"不会用"。

### 2.2 用 LangChain 搭

```python
retriever = ...            # 换成真正的 embedding 向量检索
prompt = ChatPromptTemplate(...)
chain = retriever | prompt | llm
# grounded 三重校验仍需自己写，LangChain 不保证答案真的带引用
```

要点：**框架帮你串链路，不帮你守业务红线**。数据门槛（只喂 MATCHED）、
「答案必须覆盖所问字段」这两条，无论用什么框架都得自己实现——
这正是本项目的核心价值，换框架也不会丢。

### 2.3 手写（本项目已实现）

```
build_corpus.py → 逐条查链核验，仅 MATCHED 入库
trusted_rag.py  → 检索 + 四类拦截 + grounded 三重 + 覆盖性校验 + 引用回链
server.py       → 单端口 HTTP API，可容器化
demo.py         → 20 条评测一键复现
```

## 3 面试追问标准答案

**Q：为什么不用 LangChain / Dify？**

> 不是不会用，是这次约束不划算。现场只有一台机器、一个端口，Dify 自托管至少 2 核 4 G、
> compose 还要拉向量库；LangChain 能帮我串链路，但"只喂链上核验一致的记录、
> 答案没覆盖所问字段就拒答"这些业务红线它不会替我守，还是得自己写。
> 所以我把生成层做成可插拔适配器，检索、拦截、校验、引用全部自己实现，
> 这样每一环都能查、能测、能讲清楚。
>
> 如果业务方要可视化运营 Prompt、多人协作知识库，我会选 Dify；
> 如果编排逻辑复杂到需要多轮工具和自定义重排，我会选 LangChain。
> 取舍写在仓库里，不是拍脑袋。

**Q：那如果接了真 embedding，会不会颠覆你的结论？**

> 会让检索效果变好，但不会颠覆架构：数据门槛、拒答纪律、grounded 校验都在生成层之前，
> 换检索器只影响"召回质量"，不影响"可信约束"。换了之后必须重跑 20 条评测——
> 换检索器不改评测集等于没测。

**Q：你说"拒答正确率 100%"，是不是评测集太简单？**

> 是，我主动写进 README 了。20 条里 16 条应回答、4 条应拒答，语料和问题同分布，
> 多是带批次号的精确查询，满分不等于真实准确率。
> 我还列了 6 个实测失败案例：口语泛问会串味、跨片段不比较、同名供应商有歧义等。
> 能复现的限制比含糊的满分更可信。

## 4 什么时候该改方案（升级路径）

| 触发条件 | 改动 | 影响 |
|---|---|---|
| 片段超过 10 万条 | 换 HNSW / 向量库（Milvus、Qdrant） | 检索从 40 MB 内存暴力余弦改为近似检索，需重测召回 |
| 需要语义改写、同义问法 | 接 embedding 模型 | 检索器换掉，评测集不变，指标重跑 |
| 需要多轮对话 / 工具调用 | 上 LangChain 或 Dify Agent | 生成层扩展，业务红线保持不变 |
| 客户要可视化运营知识库 | 迁 Dify | 本项目可作为"可信知识层"通过 API 接进去 |
| 现场有 GPU / 要完全离线 | 本地 Ollama + 本项目适配器 | 环境变量换 base-url，零外网调用 |

> 这五条就是"展望"该写的内容：不是画大饼，是每条都有触发条件和改动范围。
