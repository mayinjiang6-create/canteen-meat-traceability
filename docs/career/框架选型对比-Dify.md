# 框架选型对照：手写 / Dify / LangChain

> 文档编号：CAREER-07 ｜ 版本：v1.0 ｜ 定稿日期：2026-11-19
> 关联：`deploy/dify/`（知识库 + Prompt + 打分脚本）、`trusted-rag/README.md`、`项目改进清单-AI实施交付与产品岗.md`（CAREER-06）P1
> 用途：回答面试必问的「为什么不用现成框架」——用**约束能不能守住**来回答，而不是"手写更牛"

---

## 0 结论先行

| 问题 | 结论 |
|---|---|
| 这个项目为什么手写？ | 因为它的核心不是"能答"，而是**"不该答时必须不答"**：数据门槛、批次一致性、六类拦截、引用回链。这些是**输出否决权**，必须由代码持有 |
| Dify 能不能做这个场景？ | 能搭出 80% 的体验，**但拦不住最后 20%**：跨批次串台、越界推断、无依据作答，全靠 Prompt 自觉 |
| 那 Dify 有什么价值？ | 让业务方自己改 Prompt、换知识库、试点新场景，不需要发版。**它适合做"探索层"，不适合做"约束层"** |
| 面试怎么讲？ | 「我做过同场景的平台版设计并核对过每个节点的能力边界；本机没有 Docker，所以没跑实测。结论是：能用平台做原型，但红线必须留在代码里。」 |

---

## 1 为什么这个问题一定会被问

JD 里出现频率极高：「至少用过 1 种 Dify / Coze / 百炼 / N8N」「了解 LangChain / 工作流平台」。
面试官真正想知道的不是"你会不会拖节点"，而是三件事：

1. 你知道平台**替你做了什么**（切块、向量化、召回、Prompt 编排、观测）
2. 你知道平台**替不了你什么**（业务红线、结构化引用、确定性拒答）
3. 你能不能**用证据**说清这条边界，而不是凭印象

---

## 2 三方案对照

| 维度 | 手写（本项目现方案） | Dify 社区版 | LangChain |
|---|---|---|---|
| 上手成本 | 中（要写检索与拦截） | **低**（可视化拖节点） | 中高（要写代码，但组件现成） |
| 依赖 | **零**（标准库） | 8 个容器、2 核 4 GiB 起 | Python 生态 + 模型 SDK |
| 谁维护 Prompt | 开发 | **业务方也能改** | 开发 |
| 数据门槛（只收 MATCHED） | 入库前用代码过滤 | 靠导入前预处理（本仓库已导出干净语料） | 代码控制 |
| 低分拒答 | 代码阈值 + 拒绝 | 知识检索节点有 **Score 阈值** | 代码控制 |
| 越界拦截（安全/预测/写作） | 正则硬拦，**不进检索** | 只能 Prompt + IF/ELSE 分支 | 代码控制 |
| 跨批次一致性（问 A 不许答 B） | **命中集按 batchId 过滤**，空则拒答 | 需自建"抽批次 → 元数据过滤"，平台无现成节点 | 需自己写 |
| 引用结构 | `eventId / batchId / verifyStatus / score` 结构化返回 | 返回 chunk 来源，**拿不到自定义字段结构** | 自己定义 |
| 评测 | 80 条断言 + 退出码门禁，CI 可跑 | 无内置评测，需外接 ragas / langfuse | 自己写 |
| 可复现性 | `python demo.py` 一条命令 | 依赖容器与版本快照 | 依赖依赖版本 |
| 适合谁 | 有硬约束的交付型系统 | 快速原型、知识库客服、内部工具 | 需要深度定制的应用 |

> 一句话：**Dify 优化的是"搭得快"，本项目优化的是"错不了"。** 两者不冲突，位置不同。

## 3 同场景在 Dify 里怎么搭（可复现清单）

完整步骤在 [`deploy/dify/README.md`](../../deploy/dify/README.md)，这里只列骨架：

```
开始 → 知识检索（TopK=3，Score≥0.5） → LLM（deepseek-chat，温度 0.1） → 直接回复
                     └─ 可选 IF/ELSE：检索为空 → 直接回「未在已核验记录中找到依据」
```

配套文件：

| 文件 | 作用 |
|---|---|
| `deploy/dify/kb_meat_trace.md` | 190 块（186 事件 + 4 规则），每块带 eventId / 批次 / 核验状态 / 摘要 |
| `deploy/dify/build_kb.py` | 语料更新后重新生成知识库文件 |
| `deploy/dify/prompt.md` | 7 条硬约束 + 4 条对照样例（应答 / 应拒） |
| `deploy/dify/score_platform.py` | 用与 `demo.py` **同口径**给平台答案打分，拒答率不到 100% 直接非零退出 |

## 4 平台能不能守住这 7 条（逐条判定）

这是本文档的核心，也是面试时唯一值得展开的部分。

| # | 本项目约束 | Dify 能否等价实现 | 说明 |
|---|---|---|---|
| 1 | 只回答 MATCHED 事件 | ✅ 能（前置） | 导入前就把非 MATCHED 过滤掉，本仓库的导出脚本已做 |
| 2 | 答案必须带引用 | ⚠️ 部分 | 平台有引用面板，但引用是"块"，不是 `eventId`；要结构化就得把 eventId 写进块文本再解析 |
| 3 | 相似度低于阈值拒答 | ✅ 能 | 知识检索节点的 Score 阈值 |
| 4 | 无锚点泛问拒答 | ❌ 不能 | 「那批猪肉验上了没？」会检索到相似块并作答；平台没有"先判断问题是否可答"的节点 |
| 5 | 越界问题拒答（安全性/预测/写作） | ❌ 不能（只能靠 Prompt） | 可用 IF/ELSE 拼关键词分支，但每加一类就要改流程，且绕不过改写说法 |
| 6 | 点名批次只能引用该批次 | ❌ 不能 | 检索阶段不按 batchId 过滤，模型会拿别的批次凑答案——这正是本项目 held-out 抓到的真 bug |
| 7 | 引用编号越界检测 / 幻觉引用丢弃 | ❌ 不能 | 平台不做输出级校验，模型编 `[5]` 也没人拦 |

**4 条做不到、1 条部分、2 条能。** 这就是结论的由来，不是"我喜欢手写"。

## 5 实测与未实测（必须说清）

| 项 | 状态 | 说明 |
|---|---|---|
| 手写链路的 80 条评测（60 公开 + 20 held-out） | ✅ 已实测 | `python demo.py` / `python holdout.py`，数字见 `trusted-rag/README.md` |
| 知识库导出（190 块、字段完整性） | ✅ 已生成并校验 | `deploy/dify/build_kb.py`，块内含 eventId / 批次 / 核验状态 |
| 平台答案打分脚本 | ✅ 已冒烟测试 | 用 2 条样例验证判定口径与退出码 |
| **Dify 容器实跑 / 平台版数字** | ❌ **未做** | 本机 Hyper-V 已关闭（要跑 VMware 里的 FISCO 链），Docker Desktop 不可用 |
| LangChain 版 | ❌ 未做 | 与 Dify 的边界判断一致，做了也是重复劳动 |

> 面试官问"你跑过吗"——**直接说没跑，本机没有 Docker；但知识库、Prompt、打分口径都在仓库里，
> 给我一台装了 Docker 的机器，30 分钟能出数字。** 这句话比含糊其辞强得多。

## 6 什么时候该用 Dify（判断清单）

**用 Dify**

- 知识库问答、FAQ、内部文档助手，**答错代价可控**
- 业务方要自己调 Prompt、换语料，不想每次发版
- 需要快速验证"这个场景值不值得做"
- 团队没有后端，只有一个懂业务的人

**不要用 Dify（或必须把红线搬到代码里）**

- 答错会引发合规/安全/财务后果（医疗、金融、**食品安全**）
- 需要"点名实体 → 只答该实体的记录"这种**结构化过滤**
- 需要把答案回链到可审计的 ID（eventId / 订单号 / 保单号）
- 有明确的拒答率要求，且要进 CI 门禁

**混合用法（最现实）**

> Dify 做**探索层**（业务方试场景、试 Prompt、试语料），验证有效后把 Prompt 与检索参数
> **固化到代码里**做**约束层**，红线逻辑与评测集跟着代码走。这样既不挡业务创新，也不放掉底线。

## 7 面试标准答法（4 条，按追问深度递进）

**Q：用过 Dify / LangChain 吗？**

> 做过同场景的平台版设计：把 186 条链上核验过的事件导成 190 块知识库，写了 7 条硬约束的
> Prompt，并写了与手写链路同口径的打分脚本。本机没有 Docker 环境，所以平台版没有实测数字——
> 这点我不含糊。

**Q：那为什么最后不用平台？**

> 因为这个系统的价值在"不该答的时候不答"。平台能设相似度阈值，但拦不住三类：无锚点泛问、
> 越界推断、以及**问 A 批次却答 B 批次**。最后一条我在 held-out 集里真抓到过，是代码里加了
> "命中片段必须属于被点名批次"才修掉的，平台没有对应节点。

**Q：平台一点价值没有？**

> 有，位置不同。它适合做探索层：业务方自己换语料、调 Prompt、试新场景，不用发版。
> 验证有效后我再把结论固化进代码。**平台负责快，代码负责对。**

**Q：如果客户坚持要 Dify 呢？**

> 那就把红线做成外部服务：Dify 只负责生成，前后各加一道代码关卡——进检索前过滤非 MATCHED
> 与批次范围，出答案后做引用校验与拒答判定。平台当"语言层"，代码当"约束层"，验收标准不变。

## 8 如果真要上平台，升级路径

| 阶段 | 做什么 | 产出 |
|---|---|---|
| 1 | Dify 导入 `kb_meat_trace.md`，只做"事实查询"类问题 | 一个能答 39 条答案类问题的机器人 |
| 2 | 加 IF/ELSE：检索为空 → 固定拒答；关键词命中越界词 → 固定拒答 | 拒答率能到 70–85%（估算，需实测） |
| 3 | 用 Dify API 把答案回传本仓库的 `score_platform.py` | 平台版与手写版并列的数字 |
| 4 | 把"批次提取 + 元数据过滤"做成 Dify 前置代码节点（或外部微服务） | 跨批次问题闭环 |
| 5 | 输出级校验（引用编号、批次一致性）仍放在外部服务 | 平台只做生成，约束不外移 |

> 注意许可：Dify 社区版是 **Apache-2.0 + 附加限制**（多租户 SaaS 与品牌标识有约束），
> 商用前要看清；LangChain 是 MIT。这一点写进方案里，比背功能列表更能说明你上过生产。
